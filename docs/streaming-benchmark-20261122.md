# 크랙형 캐릭터 챗: 스트리밍 적용·속도·품질 재검증

측정·작성: 2026-11-22 (한국). 서비스 체감과 연속 대화 품질을 함께 확인했다. 소규모 관찰이며 SLA·블라인드 품질 동등성 검증은 아니다.

**현재 권장:** 기본 Sonnet5.5 / between_tools / 기본 high, 빠른 짧은 대화 GPT-6 Luna / none. 그래프 작품의 최종6턴 중간값은 첫 텍스트 델타2.51초 / 저장 완료8.52초와2.41초 /3.45초였다. Luna는 본문254자, Sonnet5.5는618자로 길이 차이가 컸다. 비슷한 첫 응답 체감에 접근했지만 크랙의 비공개 작가 설정까지 같은 품질이라고 입증한 것은 아니다. 공개 배포는 scene-stream/6, 사랑 작품은 정의 v2다.

## 구현 결과

- 일반 텍스트 대사를 Bedrock→AgentCore→Lambda→브라우저 전체 경로에서 스트리밍한다. 대사·기억·추천 등의 구조화 응답과 최종 상태가 완성된 뒤 한꺼번에 반환하던 대기 경로를 제거했다. 상태 필드와 이벤트 이름은 데모가 정의한 계약이다. SSE의 작은 JSON 이벤트는 즉시 전달되므로 전체 JSON 완성을 기다리는 방식과 다르다.
- 대화·최신 상태·근거 기억을 원자 저장한 후 확정 INFO를 표시한다. 그래프 투영은 DynamoDB Streams→별도 Lambda에서 비동기 갱신하며 다음 대화는 최신 스냅샷을 읽는다. 로컬 SQLite도 영속 투영 작업을 사용한다.
- 상태 해석과 게이트 계산은 대사 전에 남겼다. 현재 상태를 결정하는 일을 뒤로 미루면 본문과 INFO가 충돌하기 때문이다. 그래프 물질화에는 추가 LLM을 호출하지 않는다.
- 실패한 부분 스트림은 저장하지 않는다. 동일 requestId 재전송은 기존 결과를 반환하고 회차 잠금·버전 검사로 중복 저장을 막는다. 저장 전의 화면 대사는 임시 표시다.

## 크랙 새 실측: 연속 6턴씩

동일 작품의 새 독립 대화 2개에서 이름→작은 계획→개구리/달 이탈→5분 측정 동의→다음 준비 실행→작별까지 보냈다. 상한1500토큰, UI 생각 끄기, 한국어 서사400~800자 목표 유저노트를 적용했다. INFO는 원래 형식을 유지했다. UI 생각 끄기가 정확히 어떤 API 파라미터인지는 알 수 없다.

INFO를 제외한 서사·대사 글자 중간값은 슈퍼챗3.0 약583자, 하이퍼챗4.0 약677자였다. 이름표 등 표시 형식도 서로 다르므로 글자 수만으로 품질을 정규화할 수 없다.

두 방 모두 최종6턴을 완료하고 이름·측정 결과를 회상했다. 슈퍼챗3.0은 마지막에 “다음에 또, 불러도 될까요”라는 새 질문을 붙였고, 하이퍼챗4.0은 추가 부탁 없이 작별했다. 슈퍼챗은 4턴에 측정을 시작하고 5턴에 결과/다음 준비로 진행했다. 하이퍼챗은 4턴 안에서 측정 결과까지 내고 5턴에 새로운 연습 결과를 전개했다. 하이퍼챗은 연결의 단절·마력 소모와 같은 사건을 계속 이어 서사 전개가 풍부했다. 그것이 원작 비공개 설정인지 생성한 세부인지 공개 화면만으로 판정할 수 없다. 공개 도입만 가진 우리 테스트와 동일한 숨은 세계관 품질 비교가 아니다.

이전 조사15회와 이번 신규12회는 서로 다른 표본으로 집계했다. 계정 잔액과 비공개 회차 식별자는 이 공개 가이드에 싣지 않았다.

| 실시간 기본값에서 제외 | Grok4.7 / low | 첫 텍스트 전 약37초가 대부분을 차지했다. 내부 추론·서버 대기·라우팅 중 어느 항목이 주원인인지는 이 관찰만으로 분리하지 못했다. |

Sonnet5도 같은6턴을 완료했고 이동·이름·회상·작별을 유지했다. 이번 설정에서는 Sonnet5.5보다 완료가 느린 편이었다. 같은 이름의 모델이라도 출력 길이·입력 이력·시간대에 따라 바뀐다.

크랙 하이퍼챗4.0의 “연결 단절→선제 공급→마력 소모”처럼 여러 턴의 사건을 적극적으로 발전시키는 느낌을 목표로 한다면, 모델 선택과 함께 작가가 **확정 사실·행동 결과·시간·전이·엔딩**을 충분히 정의해야 한다. 이번 공개 도입 요약에는 그 비공개 설정이 없어 같은 서사 밀도를 복제했다고 말할 수 없다. 소환실4턴에서 Sonnet5·5.5와 Luna는 기다림을 시작하고5턴에 결과를 제시한 반면, Sol은4턴 안에5분 대기를 마쳤다. 크랙 슈퍼챗도4턴은 시작,5턴은 결과였고 하이퍼챗은4턴 안에 결과로 진행했다. 속도와 별개로 진행 템포가 다르다.

위 품질 평가는 입력·출력·저장 상태를 대조한 정성 검토다. 블라인드 사용자 평가·장기 연재 만족도 점수는 수집하지 않았다. 빠른 서비스의 출발점으로는 현재 기본값과 짧은 모드를 제공하고, 실제 작가 설정과 고객 대화로 이어지는 품질 검사를 운영하는 편이 적절하다.

### 추론 옵션은 두 축이다

- `thinking.type`은 추론을 언제/어떤 방식으로 할지 정한다. `adaptive`는 모델이 요청 복잡도에 맞춰 판단한다. `between_tools`는 Sonnet5.5에서 high 이하일 때 응답 전 추론을 생략하고 도구 사이 추론은 허용한다. 이번 대사 API에는 도구가 없으므로 도구 호출을 추가하지 않는다. `disabled`는 지원 모델에서만 전체 thinking을 끈다.
- `effort`는 응답에 쓸 토큰량·상세함에 영향을 주는 강도다. 추론만의 예산이 아니며 thinking을 생략해도 효과가 있을 수 있다. Sonnet5.5 `between_tools` + 기본 high는 모순된 설정이 아니다.
- maxTokens는 최대치이며 원하는 글자 수가 아니다. reasoning을 쓰면 그 토큰도 전체 상한을 소비할 수 있다. 길이 상한만 낮추면 INFO나 문장이 잘릴 수 있어 대사와 INFO를 분리했다. 짧은 응답 목표와 충분한 안전 상한을 함께 사용한다.

[Sonnet5.5 AWS 모델 카드](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-anthropic-claude-sonnet-5-5.html), [Adaptive thinking / 모델별 지원](https://docs.aws.amazon.com/bedrock/latest/userguide/claude-messages-adaptive-thinking.html), [Effort 정의](https://platform.claude.com/docs/en/build-with-claude/effort), [GPT Luna AWS 카드](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-openai-gpt-6-luna.html).

### 크랙 모델과 Bedrock 대안의 범위

실제 크랙 메뉴에서 슈퍼챗3.0=Sonnet5, 하이퍼챗4.0=Opus5.5를 확인해 이번 새 실측 대상으로 삼았다. Sonnet5.5는 이번 크랙 메뉴에 없었으며 Bedrock 개선 후보로 비교했다. GPT·Haiku·Nova·Grok·Gemma는 우리 데모의 대안이다. 크랙이 같은 GPT/Grok 모델을 제공한다고 주장하지 않는다.

크랙 메뉴에는 Fable5, Opus5/4.8/4.7/4.6, Sonnet4.6/4.5, Gemini4/3.1Pro/2.5Pro도 표시됐다. 이번 신규14종 비교는 데모의 선택 가능 모델을 대상으로 하므로 이 목록 전체의 최적 조합을 찾았다는 의미는 아니다. Gemini와 Gemma는 다른 제품군이다. Gemini는 이번 Bedrock 카탈로그에 없어 같은 모델의 Bedrock 비교를 수행하지 않았다. Fable와 옛 Claude 버전은 이번 스트리밍 재검증 대상에서 제외했으며, 앞선 조사에서 Opus4.7 등의 별도 실측이 있었다.

HTTP Date는 응답 헤더 시각(초 단위)이고 추론 시작 시각으로 해석할 수 없다. 본문 첫 조각은 표시 태그를 뺀 텍스트의 클라이언트 수신 시각이며 브라우저 paint가 아니다.

### 측정과 품질의 한계

단일 한국 클라이언트, 모델별3회 또는 연속6턴, 시간대·출력 길이·숨은 설정·API가 달라 통계적 순위나 장기 몰입 동등성을 입증하지 못한다. 현재 최근6턴 원문과 최대16개 근거 기억을 사용하며 임베딩 검색·무한 장기 기억은 없다. 추론을 줄여도 필요한 설정·기억을 입력하지 않으면 인물의 일관성이 생기지 않는다.

그래프 엔진은 등록된 수치·전이·엔딩을 검증하지만, 자유 텍스트의 모든 사실이 그래프와 일치함을 증명하지 않는다. 스트리밍에는 생성 후 전체 답변을 미리 검사할 수 없다는 특성도 있다. 이번에는 사후 LLM 검수·재생성을 추가하지 않고 확정 상태를 선행 제공해 제어한다. 엄격한 본문 일치 보장이 필요하면 제약된 장면 템플릿·행동 DSL 등 별도 설계가 필요하며 자유 서술 폭과 체감 속도의 절충이 생긴다.

[AgentCore SSE 계약](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-http-protocol-contract.html), [Lambda 응답 스트리밍](https://docs.aws.amazon.com/lambda/latest/dg/config-rs-write-functions.html), [DynamoDB Streams 소비자 중복 처리](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.Lambda.BestPracticesWithDynamoDB.html).

### 비용과 저장의 절충

그래프 작품은 입력 해석·기억을 한 보조 호출에 합쳐 대사와 총2회 모델 호출을 사용한다. 일반 작품은 대사·기억 추출·조건/이미지 판정으로 최대3회이며, 적용할 규칙이 없으면 판정 호출은 생략한다. 병렬화는 기다림을 줄이지만 보조 모델의 토큰 비용을 없애지는 않는다. 그래프 투영 자체에는 LLM 비용이 없다. 일반 작품에서 기억 추출 실패는 빈 신규 기억으로 처리해 완성된 대화를 저장하고, 그래프의 필수 입력 해석 실패는 상태를 진행시키지 않는다. 장기 기억 품질을 엄격히 요구하는 운영판에서는 재추출 작업·모니터링을 추가해야 한다.

이번 데모는 24턴/회차, 최근6턴 원문, 근거 기억 최대16개, DynamoDB7일TTL과 전체 하루500턴으로 범위를 제한한다. 이 수치는 운영 용량 설계나 장기 서사 품질 보장이 아니다. 웹 Lambda 동시성10도 데모 제한이므로 다중 고객 규모에서는 대기열·쿼터·부하 검증이 추가로 필요하다.

### 작가의 행동과 전이를 연결하기

개발 중 첫72턴은 저장·새로고침·그래프 투영이 모두 성공했지만, 일부 본문은 밖으로 걸어가고 상태는 창가에 남았다. 후속18턴에서도 행동 카운터는 올랐으나 전이 ID 누락으로 같은 문제가 재현됐다. 이 진단 결과를 최종 성공 표본에 합치지 않았다.

그래서 선택형 작가 규칙 `Action.opensTransition → Transition`을 추가했다. 근거가 확인된 행동이 작가가 연결한 이동을 요청하며, 기존 최소 턴·카운터·전이 게이트를 그대로 통과해야 한다. 모델의 전이 ID가 빠져도 별도 LLM 호출 없이 처리한다. 서로 다른 목적지 후보가 충돌하면 자동 선택하지 않는다. 원문에 없는 행동·근거 없는 이동은 허용하지 않는다. 행동 정의의 참조 관계로 처리하므로 표현과 언어가 달라도 같은 규칙을 적용한다. 사랑 작품 정의는 v2로 올렸고 기존 회차의 핀은 유지하므로 새 회차로 확인해야 한다.

화면의 모델 토큰 사용량은 대사 모델 기준이며 보조 모델 비용까지 합산한 청구서가 아니다. 처리 시간의 보조 단계는 병렬로 중첩된다. 저장된 그래프 투영의 관찰 지연도 한국 클라이언트의 재조회·폴링을 포함하며 AWS Lambda 실행시간 자체가 아니다.

## 실제 병목과 검증 결과

최종72턴의 회차 재조회와 그래프 버전 일치는72/72였다. 사랑 작품은6개 모델 모두4턴에 school-road,6턴에 until-next-time을 확정했다. 입력 해석 중간값1,525ms(n=36), 상태 규칙 계산4ms(n=36), 원장 저장11.5ms(n=72), AgentCore 스트림 연결149.5ms(n=72)였다. 첫 세션의 연결은 최대1,907ms로 콜드 시작이 섞였다. 단계는 중첩되며 합산한 값이 전체 요청 시간은 아니다.

**핵심 병목은 대사 생성 길이와 선행 입력 해석이다.** 그래프 작품에서 Luna로 바꿔도 첫 조각은2.51→2.41초로 차이가 작았다. 짧은 응답으로 전체 완료를 줄이는 효과는 컸다. DB 저장이나4ms 수준의 규칙 계산을 비동기화하는 것만으로 큰 체감 개선이 생기지는 않는다. 전체 그래프 투영은 응답 경로에서 분리해 일관성을 지켰다. 현재 작은 그래프는 전체 재구성·버전 저장 방식이며 대규모 운영에서는 변경 이벤트별 투영 비용을 별도로 평가해야 한다.

첫 텍스트 델타에는 [행동] 같은 표시 태그도 포함될 수 있으므로 실제 본문 표시보다 빠를 수 있다. 아래 브라우저 검사는 표시 태그를 제거한 첫 본문을 DOM에 넣는 코드 시각을 따로 기록했다. 컴포지터의 픽셀 paint를 직접 측정한 것은 아니다.

| 공개 브라우저 확인 | 모델 | 첫 본문 DOM 삽입 | 관찰 완료 |
|---|---|---:|---:|
| English | GPT-6 Luna | 4.14초 | 4.79초 |
| 日本語 | Sonnet 5 | 3.63초 | 7.72초 |
| 한국어 · 창가 대화 | Sonnet 5.5 | 2.54초 | 7.11초 |
| 한국어 · 하굣길 전이 | Sonnet 5.5 | 2.77초 | 9.94초 |
| 한국어 · 기억과 위치 회상 | GPT-6 Luna | 2.79초 | 4.19초 |

각 행은 서로 다른 언어/턴의 기능 확인1회로, 모델 속도 순위용 표본이 아니다. 영어→일본어→한국어를 바꿔도 이름·푸딩·현재 위치가 이어졌고,5턴 후 새로고침해 대화와 INFO가 그대로 복원됐다. Sonnet5.5 한국어 출력은32→425자, 이동 턴은26→637자로 점진적으로 늘어났다.

자동 검사22개(스트림 분할·실패·중복 재시도·저장 복원·그래프/전이/엔딩·구버전 호환)가 통과했다. 소스 ZIP v1.1.0을 독립 설치해15개 검사·빌드·CDK synth가 통과했다. 실제 CloudFormation UPDATE_COMPLETE, Runtime READY와 그래프 실패 큐0건을 확인했다. 이 보고서는 원본 사용자 대화·쿠키·비공개 회차 링크를 포함하지 않는다.

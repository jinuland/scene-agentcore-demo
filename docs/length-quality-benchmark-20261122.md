# Grok 4.3·Sonnet 5.5: 실제 답변 길이를 맞춘 비교

2026-11-22 · 한국 Mac → Amazon Bedrock 직접 스트리밍 측정. 고객의 목표는 짧은 답변으로 수치만 줄이는 것이 아니라, 크랙형 이야기 서비스를 충분한 분량과 일관성으로 제공하는 것이다.

**판단:** Grok 4.3 / none은 실제 길이가 비슷한 답변에서도 완료가 빨랐다. 다만 길이 제어와 시간·세부 사실·문장의 자연스러움에서 문제가 관찰됐다. 현재 데모 기본값은 **Sonnet 5.5 / between_tools**를 유지한다. Grok은 속도 우선 후보로 제공하되, 긴 이야기의 품질이 같은 수준이라고 권장하지 않는다.

## 길이를 어떻게 맞췄나

1. 첫 재회, 편지 봉인·다음 약속, 스타워즈 호송의 세 장면을 준비했다. 각 장면의 확정 그래프 상태·최근 대화 원문·현재 입력은 고정했다. 같은 입력으로 준비한 상태를 두 모델에 전달했다.
2. 먼저 **똑같은 550~750자 지시**로 모델별 각 9회, 총18회를 측정했다. Grok은 실제276~503자(목표 충족0/9), Sonnet은680~843자(5/9)였다. 이 집합의 완료시간으로 같은 분량의 속도 우위를 주장하지 않는다.
3. 분량만 보정한 별도18회를 실행했다. Grok에는1400~1600자, Sonnet에는500~650자를 요청했다. 나머지 시스템 지시·장면·입력과 출력 상한2200토큰은 동일하다. 실제 출력은 Grok563~953자, Sonnet568~763자였다. **보정 단계에서는 분량 요청이 다르므로 완전히 동일한 프롬프트 A/B가 아니다.**
4. 보정18회 안에서 같은 장면끼리 실제 길이 비율이1.15 이하인 쌍을 찾았다. 가능한 쌍 수를 최대화하고, 그다음 글자 수 차이 합을 최소화했다. 한 응답은 한 번만 쓴다. 속도나 품질을 기준으로 쌍을 고르지 않았다. 9쌍 중5쌍이 비교 가능했다. 남은8개 응답도 원자료에 포함했다.
5. 응답을 자르거나 덧붙이거나 실패 길이만 재생성하지 않았다. 태그를 제외하고 공백을 한 칸으로 합친 뒤 NFC 정규화한 Unicode 글자 수를 센다. 공백은 포함한다. 일부 조합의 차이는 최대15% 남으므로 토큰 수·의미 내용이 완전히 같다는 뜻은 아니다.

## 길이가 비슷한 5쌍 결과

| 모델·옵션 | 실제 본문 길이 중간값(범위) | 첫 본문 델타 중간값 | 정상 스트림 완료 중간값 |
| --- | ---: | ---: | ---: |
| Grok 4.3 / reasoning_effort none | 756자 (604~856) | 0.57초 | 3.22초 |
| Sonnet 5.5 / thinking between_tools | 739자 (601~763) | 0.88초 | 8.86초 |

이 표의 완료 중간값 차이는 약64%다. 이는 **선택된5쌍·Bedrock 직접 호출**의 관찰이며 서비스 전체가64% 빨라진다는 뜻은 아니다. 한국 Mac의 요청 직전부터 첫 text delta 또는 정상 스트림 종료까지 측정했다. 네트워크·클라이언트·모델 대기 및 생성은 포함하고, AgentCore·웹·Haiku 입력 해석·DB 저장·브라우저 paint는 제외한다. AWS 내부의 순수 추론 시작·종료시각을 뜻하지 않는다. `between_tools`는 도구 호출 사이의 생각을 허용하는 모드이고 이번 대사 요청은 도구를 제공하지 않는다. `none`은 Grok4.3의 추론 비활성 요청이다. [설정 용어와 기존 크랙 비교](streaming-benchmark-20261122.md)를 함께 참고한다.

각 장면/모델3회, 동시 요청2개, 순서를 라운드별 교대했다. Sonnet은 서울 리전에서 global 모델 프로필로 ConverseStream, Grok은 us-east-1 Bedrock Mantle의 OpenAI 호환 스트림을 사용한다. 모델뿐 아니라 엔드포인트·프로토콜·리전 경로도 다르다. implicit caching과 순간 부하를 통제하지 않았고 일부 Grok 사용량에 cache hit가 있다. SLA·p95·동시 사용자 용량·블라인드 선호도 검증은 아니다. 이번 작업에서는 크랙을 새로 실측하지 않았으며, 이전 크랙 실측과 위 Bedrock 단독 수치를 같은 구간의 수치처럼 직접 빼지 않는다.

## 실제 대화 품질에서 본 차이

5쌍의 원문을 사람이 읽고 비교한 정성 평가다. 아래는 관찰 가능한 예시이며 통계적 품질 점수는 아니다.

| 확인 항목 | Grok 4.3 | Sonnet 5.5 |
| --- | --- | --- |
| 기본 선택 유지 | 봉인된 편지·천천히 관계를 정한다는 의사·우회 항로·연료60%는 유지했다. | 같은 핵심 선택을 유지했다. |
| 현재 시간 | 재회 첫 답변에서 확정된 늦은 밤을 ‘오후 늦은 빛’으로 표현했다. | 대응 답변은 ‘늦은 밤의 파형’으로 유지했다. |
| 수치 근거 | 호송 답변에서 ‘아직10분 정도 여유’라고 했지만 경과5분·검문시한10분이다. 다른 답변의 ‘속도0.6’도 상태에 없다. | 대응 답변에서 연료60%와 아직 합류 전이라는 사실을 유지하고 남은 분 수를 새로 확정하지 않았다. |
| 이야기 전개 | 한 답변은 카페 재회 뒤 열리는 B-12 확인을 ‘오늘 밤10분만 더’ 하자고 앞당겼다. 잔·손끝·시선 묘사가 반복되는 경향도 있다. | 봉인과 관계 경계를 대사 안에서 비교적 자연스럽게 받고 다음 약속으로 연결했다. |
| 남는 한계 | 분량 요청1400~1600에도563~953자로 편차가 컸다. 길이를 늘리는 프롬프트만으로 품질이 따라오지 않았다. | 역시 분량을 정확히 지키지 않고, ‘오늘은…나가자’며 사용자가 요청하지 않은 마무리를 제안하거나 설정에 없는 공지·오전 일정 등을 보탰다. 완전한 사실 준수는 아니다. |

예시 입력: “내일 오후, 조용한 카페에서 만나자. 다만 예전 연인으로 바로 돌아가자는 뜻은 아니야. 오늘 편지는 열지 않기로 한 것도 기억해 줘.”

- Grok은 봉인과 관계 경계는 수용했지만 한 응답에서 “오늘 밤에 마지막으로 확인하고 싶은 게 하나 있어…카페로 가기 전에 이 가게에서10분 정도만 더”라며 후속 사건 순서를 앞당겼다.
- Sonnet은 “2년을 오늘 밤 안에 되감을 수는 없으니까…지금의 우리가 어떤 사람들인지 천천히 보는 걸로”라고 현재 의사를 받아들이고, 오후 세 시는 확정이 아닌 제안으로 표현했다.

그래프는 잘못된 문장이 DB의 정식 사건·수치·엔딩으로 저장되는 것을 제한한다. **모든 생성 문장이 그래프와 일치하도록 강제하는 것은 아니다.** 별도 LLM 검수나 재생성은 추가하지 않았다. 더 엄격한 서비스는 허용 수치/시간을 별도 표시하고 품질 기준에 맞는 모델·프롬프트를 선택해야 한다.

## 서비스 설정에 적용한 것과 적용하지 않은 것

- 대화창에 **장면형·길게 / 대화형·짧게**를 추가했다. 기본은 장면형이다. 현재 배포는 두 모델 모두 공통 장면형 목표550~750자(한국어)를 쓴다. 이는 희망 분량이며 출력 보장이 아니다. Grok이 짧게 쓰는 문제가 남아 있음을 명시한다.
- 위 실험의 Grok1400~1600자 보정은 비교용이다. 다른 사전 탐색에서는1207자까지 길어지고 묘사·수치 오류가 늘어, 제품에 일괄 적용하지 않았다. 빠른 수치를 만들기 위해 본문을 임의로 늘리거나 자동 재생성하지 않는다.
- Grok4.3의 reasoning none을 유지한다. Low 탐색3회는 본문322~469자, 첫 델타3.39~7.71초였다. 긴 분량 확보에 도움이 되지 않고 첫 응답이 늦어졌다.
- 이야기 중심 고객 데모는 Sonnet5.5 장면형을 우선한다. 지연을 가장 낮추려는 고객은 Grok4.3 none을 후보로 삼되 자체 작품의 시간·고유명사·게이트·반복률을 별도로 평가해야 한다.
- 출력 토큰 상한을 같게 둔 것만으로 동일 분량 비교가 되지 않는다. 실제 글자 수·첫 델타·완료·사용량을 함께 남겨야 한다.

[원문·설정·전체 응답 및 실제 길이](length-quality-data-20261122.json)에 공통 프롬프트18회, 분량 보정18회, 추가 탐색 결과와 고정 문맥을 수록했다. 실제 사용자 대화는 포함하지 않았다.

## ‘한 잔 더’가 엔딩이던 문제

이전 record-world v1은 meet-again 카운터를 최종 엔딩 조건으로 썼다. Grok이 임의로 회차를 끝낸 것이 아니라 작품 규칙이 너무 일찍 입력창을 잠근 것이다.

v2는 커피 약속·오늘의 인사를 **Milestone(중간 진행)**으로 분리한다. 같은 회차에서 약속 정하기 → 명시적으로 다음 날 카페 도착 → 반납표 확인 → B-12 관리 기록 확인 → 음반 정리 → 관계 선택으로 이어진다. 개인 편지를 봉인한 선택과 관리용 기록은 구별한다. 약속 제안만으로 시간이나 장소를 건너뛰지 않는다.

‘다시 연인으로’, ‘친구로’는 후속 사건을 마친 뒤 명시적으로 선택해야 최종 엔딩이 된다. ‘앞으로 더는 만나거나 연락하지 않겠다’는 최종 관계 정리도 별도 엔딩이다. 오늘 밤 인사만으로 관계를 종료하지 않는다. 결정을 미루고 대화할 수 있다. 현재 데모에는 회차24턴 상한이 별도로 있다.

기존 v1 회차는 원문·선택·시간·근거 이력을 보존하면서 새 진행 규칙으로 한정 업그레이드한다. GET 조회는 저장하지 않고, 다음 정상 턴에서 새 정의와 상태를 원자 저장한다. 다른 작품의 고정 규칙은 바꾸지 않는다.

## 배포 검증

공개 서비스 `scene-stream/10`에서 Sonnet5.5 새 회차11턴과 Grok4.3 v1 종료 회차 업그레이드8턴을 별도로 실행했다. 총19턴의 매 저장 후 재조회가 일치했다. 업그레이드 GET은 DB v1을 그대로 두고, 다음 턴에서 v2와 원문 이력을 함께 저장했다. 오늘의 인사는 between-days, 실제 도착은 cafe-reunion으로 진행됐고 후속 기록 확인 뒤 연인·친구 엔딩에 각각 도달했다. 두 회차의 비동기 그래프가 마지막 버전에 수렴하고 Milestone 노드를 포함함을 확인했다. 테스트 회차만 삭제했다.

이19턴은 서로 다른 대화 길이와 캐시·워밍업·동시 실행이 섞인 기능 확인이다. 이를 동일 길이 속도 비교의 표본에 합치지 않았다. 별도의 조합이므로 단독 모델 첫 델타 수치를 서비스 전체 지연의 보장으로 사용하면 안 된다.

소스39개 자동 검사와 타입 검사를 통과했다. 독립 배포 ZIP에는32개 검사를 포함한다. 브라우저에서는 실제 사용자7턴을 추가·삭제하지 않고, 같은 회차의 입력창 재활성화·중간 진행·다음 약속 추천·길이 선택을 확인했다.
